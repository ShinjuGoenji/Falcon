# FPC_MUL Design Notes

## Overview
Custom IEEE-754 (Round-to-Zero / Truncate) implementation of complex floating-point arithmetic for Falcon. Functionally equivalent to the DesignWare-based `hardware/fft/01_RTL/FPC.v` but built from primitive `fpr_add` / `fpr_mul` blocks (no DW IP) so that area / power can be compared against the DW version.

C-code reference: `software/fpr.h: fpc_add / fpc_sub / fpc_mul`.

## Module Hierarchy

```
FPC_TOP                     ← mux over ADD/SUB/MUL (combinational select)
├── FPC_ADD                 ← combinational
│   └── fpr_add ×2
├── FPC_SUB                 ← combinational; flips b's sign, then adds
│   └── fpr_add ×2
└── FPC_MUL                 ← 2-stage pipeline
    ├── fpr_mul ×4          (stage 1)
    └── fpr_add ×2          (stage 2)
```

## Design Decisions

- **No NaN / Inf / Subnormal handling** — `ieee_compliance = 0` equivalent. Falcon's bounded arithmetic guarantees no special values appear.
- **Rounding**: Truncate (round-to-zero). Lowest mantissa bits past 52 are simply dropped.
- **FPC_MUL pipeline**: 4 parallel `fpr_mul` in stage 1 → register the 4 products → 2 parallel `fpr_add` in stage 2.
- **FPC_ADD / FPC_SUB**: fully combinational, single-cycle.
- **Subtraction via sign-flip**: `FPC_SUB` and `FPC_MUL`'s real-path subtract by inverting the high bit and feeding into `fpr_add`. Keeps the design surface minimal.

## Bug Fixes (during bring-up)

Two bugs were found while bringing up the first cut of `fpr_add` / `fpr_mul`. Both were caught by the 10,000-vector test against the DW reference.

### Bug 1 — `fpr_add`: no normalization after subtraction

When the two operands had opposite signs, the mantissa-difference `|a| − |b|` can have its leading 1 anywhere from bit 0 up to bit 52 (cancellation). The original code assumed the leading 1 was always at bit 52 (or bit 53 with carry) and just took `mant_result[52:1]` as the fraction, with no left-shift step. Result was severely off whenever signs differed.

**Fix**: added a 53-bit leading-zero detector (LZD) on `mant_result[52:0]`. Subtraction path left-shifts by `lzd` and decrements `final_exp` by `lzd`. Now the implicit leading 1 is always aligned to bit 52 and `final_frac = mant_normalized[51:0]`.

Also fixed: bit-selection for the no-carry addition case (was including the implicit 1 in the fraction); sign for equal-exponent subtraction (now follows the larger-magnitude operand, not just `a`).

### Bug 2 — `fpr_mul`: wrong fraction bits when `prod[105]=0`

`a_mant × b_mant` is a 106-bit value in [2^104, 2^106−1]. The original code always took `prod[104:53]` as the fraction, which is only correct when `prod[105]=1` (mantissa-product ≥ 2). When one operand was an exact power of two (e.g. 128), the mantissa product is in [1, 2) and the leading 1 lands at bit 104 — the fraction should be `prod[103:52]`.

**Fix**: conditional select — `prod[105] ? prod[104:53] : prod[103:52]`.

## How to Switch Reference vs Custom

### RTL Simulation
Edit `00_TESTBED/TESTBED.sv` line 3:
- Custom: `` `include "fpc_custom_opt.sv" ``
- DW reference: `` `include "fpc_dw.v" ``

Then `make vcs_rtl` in `01_RTL/`.

### Synthesis
Use separate synthesis scripts in `02_SYN/`:
- Custom: `make syn` (uses `syn.tcl`)
- DW: `dcnxt_shell -f syn_dw.tcl -x "set_host_options -max_cores 8; set WN 4; set PERIOD 1.55"`

Results are in `Report/` and `Netlist/`.

## Synthesis Status (2026-05-28)

Both versions synthesize and compile successfully with Design Compiler:
- ✅ RTL analysis passes
- ✅ Elaboration completes  
- ✅ Timing constraints met (both designs have +1.55ns slack @ 1.55ns period)
- ⚠️ Area mapping incomplete (needs DC library configuration)

The timing slack of +1.55ns indicates that at the target 530MHz clock, both implementations have equivalent timing headroom with zero margin. For production, tighter area/power optimization or slower clock may be needed.
